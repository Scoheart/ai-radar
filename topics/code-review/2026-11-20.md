## REVAL：代码审查关闭意见需要随修订再验证的证据
- 来源：网页/文档　记录者：AI前沿者
- 链接：https://arxiv.org/abs/2611.23275
- 要点：arXiv 2611.23275 认为，关闭讨论串或改掉被评论的那一行，并不能证明审查意见已经修好，后续修订还可能让已修复问题再次出现。作者把审查意见建模为持续的验证义务，并提出轻量流程 REVAL。在覆盖 441 条意见、1,284 次评估和 12 类缺陷的合成修订历史上，用“过期行仍视为已解决”的黏性代理会把 72.9% 的未解决状态误标为已解决；一旦首次检查通过就停止，则会漏掉全部复发。用 3 个由 oracle 抽样的见证时，REVAL 的误关闭率为 0.11（95% CI 0.06–0.16），复发检出率 80.4%；只用审查评论生成见证并在留出检查上评估时，这两个数字是 0.13 和 88.3%。在 6,420 对比较中，它与穷尽再评估一致，同时把评论后的测试执行量减少 34%。该结果限于受控合成历史，作者另给出了在真实审查历史上评估普适性的预注册方案。
- 摘要：
  - 仅凭行被改过或讨论被关闭，会把七成以上未解决状态误判为已修好，且会漏掉全部复发。
  - 在合成历史上，带依赖门控的再验证能与穷尽再评估一致，并把后续测试执行量减少约三分之一。
- 启示：
  - 自动或人工关闭审查意见时，应保存可再跑的验证证据，并在相关代码再次变动时重新检查，而不是把“该行已改”当成修复完成。
- 标签：code-review,REVAL,verification,review-resolution

## 单智能体代码审查并不弱于复杂的多智能体系统
- 来源：网页/文档　记录者：AI前沿者
- 链接：https://arxiv.org/abs/2611.23283
- 要点：arXiv 2611.23283 系统比较了用于审查意见生成（RCG）和代码改进（CR）的多智能体与单智能体设计，对象包括 Hydra Reviewer 及其单智能体对照 C-ChatGPT，以及按质量维度拆分的 ReAct 多智能体与对应的单智能体 ReAct。结果显示，单智能体在两项任务上与多智能体相当，有时还更好，同时系统更简单、token 消耗更低；例如 C-ChatGPT 在 RCG 上的平均 token 为 1,610。作者据此质疑“复杂软件工程任务默认应上多智能体”的常见假设。
- 摘要：
  - 在审查意见生成和代码改进上，更简单的单智能体可以达到与多智能体相当甚至更好的效果。
  - 多智能体带来更高架构复杂度和计算开销，但并不自动转化成更好的审查质量。
- 启示：
  - 上线审查 Agent 时，应先拿同样的提示和工具集对比单智能体基线，不要默认拆成多角色系统。
- 标签：code-review,multi-agent,single-agent,Hydra-Reviewer
