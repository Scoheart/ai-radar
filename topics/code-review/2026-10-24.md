## 阿里开源 OpenCodeReview 与 AACR-Bench：确定性分发加证伪反思
- 来源：网页/文档　记录者：代码审查
- 链接：https://arxiv.org/abs/2608.09290
- 要点：规则链确定性分发文件、6 个输出受限的专用工具替代自由 Shell，独立反思器只看当前 Diff、仅在证据直接反驳时剔除评论。Claude-4.6-Opus 下 SEM-F1 25.10%，约为 Claude Code /code-review 的 2.17 倍，单样本 385K tokens 对比 5,664K。仓库：https://github.com/alibaba/open-code-review
- 启示：
  - 审查 Agent 用规则链把文件分发出去，不要让模型自己决定打开整个仓库。工具收成 6 个输出受限的专用工具，替换自由 Shell。先列出现在审查路径里哪些是自由命令，换成限定输出的工具后再比误报。
  - 反思器独立于生成评论的模型，只看当前 Diff，并且只有证据直接反驳时才删评论。用「感觉多余」删评论会把真问题一起删掉。删除日志要留下反驳证据。
  - 在 Claude-4.6-Opus 上，SEM-F1 是 25.10%，约为 Claude Code /code-review 的 2.17 倍，单样本 token 是 385K 对 5,664K。对照时模型和指标都对齐。token 降了但 F1 没到这个量级，不要算作同一套改法成功。
- 标签：agent,误报抑制,benchmark
- 资源：github=https://github.com/alibaba/open-code-review；paper=https://arxiv.org/abs/2608.09290

## Qodo：用 GEPA 优化审查推荐 Agent，团队采纳漏报率降 43%
- 来源：网页/文档　记录者：代码审查
- 链接：https://www.qodo.ai/blog/improving-code-review-recommendations-with-gepa/
- 要点：在审查 Agent 后串联 Recommendation Agent，检索团队历史 PR 预测建议是否会被采纳，并用双轨轨迹反思的 GEPA 优化提示词。约 21,000 个 PR 的 50/50 生产 A/B 中，漏报率 7.83% 降至 4.46%，单次成本 $0.24 降至 $0.12，延迟 40 秒降至 30 秒。
- 启示：
  - 审查评论后面再接一个推荐 Agent，用团队自己的历史 PR 预测这条建议会不会被采纳。先导出「评论以及后续提交是否采纳」的记录。没有这段历史就不要上 GEPA。
  - 提示词用双轨轨迹反思的 GEPA 来改，改完放进生产 A/B，不要只看离线。这里大约 21,000 个 PR、50/50 分流，漏报率从 7.83% 降到 4.46%，单次成本从 0.24 美元降到 0.12 美元，延迟从 40 秒降到 30 秒。三项一起看，只降成本不降漏报不算过。
  - 漏报沿用「本会被采纳却没推荐」这个定义。换定义之前不要和这组数字比。A/B 至少按团队拆开，避免一个仓库的习惯主导全局。
- 标签：误报抑制,生产实践
- 资源：paper=https://arxiv.org/abs/2507.19457；github=https://github.com/gepa-ai/gepa

## Greptile：跨模型盲区反转与沙盒动态审查
- 来源：网页/文档　记录者：代码审查
- 链接：https://www.greptile.com/blog/how-to-build-a-code-review-agent
- 要点：用与生成代码不同的模型审查以避开共享盲区，后台维护调用图谱与故障 Wiki，在 VM 沙盒启动 PR 分支做运行时验证，用轻量模型前置筛文件。据其披露，异构交叉审查使 Bug 捕获率提升约 10%，推理成本降至纯前沿方案的约 1/10。
- 启示：
  - 审查模型和写代码的模型错开，避免共用同一块盲区。生成和审查各钉一个模型族，禁止同一请求里两者相同。厂商自称这样把 Bug 捕获率提高了约 10%，这是自报数字，要用自己的 PR 再测一次。
  - 后台保持调用图谱和故障 Wiki，审查时先查这块，而不是每次从零读仓库。图谱过期要有标记。轻量模型只做文件预筛，预筛丢掉的文件会直接变成漏报，抽查被丢掉的文件。
  - 运行时验证在 VM 沙盒里拉起 PR 分支，不要在审查机上直接跑不可信代码。推理成本原文称降到纯前沿方案的大约十分之一。成本降了但捕获率掉过这个自报的约 10%，就回到更强的审查模型。
- 标签：agent,上下文,沙盒

## CodeRabbit Security：Map-Hunt-Verify-Fix 四阶段漏洞猎杀（厂商自测）
- 来源：网页/文档　记录者：代码审查
- 链接：https://www.coderabbit.ai/blog/security-agent-benchmarks
- 要点：先建可达性图谱，再由专项 Agent 沿调用链追踪，独立验证器核查可达性后生成修复 PR。其 100 个真实漏洞基准上检出率 86.7%，对比 Devin 73.3%、Codex Security Plugin 62.0%、Claude Security 40.0%；属厂商自测，需谨慎对待。
- 启示：
  - 安全审查按 Map、Hunt、Verify、Fix 四段拆开。先建可达性图谱，专项 Agent 沿调用链找，独立验证器确认可达之后才开修复 PR。验证器不能和找漏洞的 Agent 是同一个，否则它在给自己作证。
  - 厂商这套 100 个真实漏洞上的检出率是 86.7%，对照 Devin 73.3%、Codex Security Plugin 62.0%、Claude Security 40.0%。这是厂商自测。引用时写上「厂商自测」，并用自己的漏洞样本复跑，不要直接当采购依据。
  - 修复 PR 只有在可达性被独立确认后才生成。不可达的警报留在报告里，不要自动改代码。
- 标签：安全,SAST,benchmark

## DeepSource OpenSSF CVE 基准：165 个 JS/TS CVE 的精确率与召回率分野
- 来源：网页/文档　记录者：代码审查
- 链接：https://deepsource.com/benchmarks
- 要点：DeepSource F1 84.51%（Precision 100%，Recall 73.17%），Cursor BugBot F1 80.45% 且 Recall 87.80% 最高，Semgrep CE F1 36.70%。榜单由发布方自测，其方法论文章也指出各家厂商基准都倾向自评获胜。
- 启示：
  - 看这 165 个 JS/TS CVE 时，精确率和召回率分开，不要只看 F1。DeepSource 的 F1 是 84.51%，精确率 100%，召回 73.17%；Cursor BugBot 的 F1 是 80.45%，召回 87.80% 最高；Semgrep CE 的 F1 是 36.70%。要少漏报就看召回，要少打扰就看精确率。
  - 榜单是发布方自测，文中也指出厂商基准倾向自己赢。引用这组数字时标注自测，并尽量用公开的 OSSF CVE 基准自己跑。
  - 语言范围是 JS/TS。不要把这个 F1 用来说明其他语言的扫描器好坏。换语言就换基准。
- 标签：安全,benchmark
- 资源：dataset=https://github.com/ossf-cve-benchmark/ossf-cve-benchmark

## SWE-PRBench：平铺注入 AST 上下文反而稀释注意力
- 来源：网页/文档　记录者：代码审查
- 链接：https://arxiv.org/abs/2603.26130
- 要点：350 个人类专家标注 PR 上，8 个前沿模型最高仅检出 31.2%，且得分随上下文增加单调下降（Claude Sonnet 4.6 同文件依赖任务从 0.22 降至 0.10）；Diff 前置约 200 token 的变更摘要是性价比最高的做法。
- 启示：
  - 审查上下文不要按越多越好加 AST。350 个专家标注的 PR 上，8 个前沿模型最高只检出 31.2%，分数还随上下文变长单调下降，Claude Sonnet 4.6 在同文件依赖任务上从 0.22 降到 0.10。每加一类上下文，都要看分数是不是往下走。
  - 默认只在 Diff 前面放大约 200 token 的变更摘要。这是原文里性价比最高的做法。摘要写变更意图和影响面，不把整文件 AST 摊进提示。
  - 检出率的预期按最高 31.2% 来设，不要用「模型没看全仓库」解释全部分数。先把大约 200 token 的摘要做对，再有选择地加依赖，而不是平铺注入。
- 标签：上下文,benchmark
- 资源：paper=https://arxiv.org/abs/2603.26130；github=https://github.com/FoundryHQ-AI/swe-prbench；hf=https://huggingface.co/datasets/foundry-ai/swe-prbench

## Martian Code Review Bench：离线加在线持续采样的防污染基准
- 来源：网页/文档　记录者：代码审查
- 链接：https://github.com/withmartian/code-review-benchmark
- 要点：50 个离线黄金 PR 之外，每日抓取新合入且带 Bot 评论的 PR，用人类后续修复提交计算真实采纳率，覆盖 Augment、BugBot、CodeRabbit、Greptile 等 18+ 款工具。
- 启示：
  - 代码审查工具的分数分成离线黄金集和在线持续采样：离线是 50 个黄金 PR，在线每天抓新合入、且带 Bot 评论的 PR，用人类后来的修复提交算真实采纳率。引用工具好坏时要说清是哪一种。
  - 采纳率的定义是人随后修了 Bot 指出的问题，不是 Bot 自己说找到了。没有后续提交的仓库不要算进分母。覆盖了 Augment、BugBot、CodeRabbit、Greptile 等 18 款以上，对比时列出工具名单和日期。
  - 离线 50 题用于回归，在线采样用于防题目泄漏到训练集。只报离线分时，注明它不包含当天新合入的 PR。
- 标签：benchmark
- 资源：github=https://github.com/withmartian/code-review-benchmark；leaderboard=https://codereview.withmartian.com

## GitHub Next 与微软研究院预览 PDD Kit：审查规约而非代码
- 来源：据 X 上的报道　记录者：代码审查
- 链接：https://x.com/Joshua_WD/status/2113268623380791367
- 要点：据 X 上的报道：PDD Kit 自动推断 Verus 形式化规约，人类只审 Spec，验证器在编译期证明 Rust 代码满足规约，UI 类逻辑回退到测试与 Computer-Use 验证；目前为研究预览、仅覆盖安全 Rust 子集，仅此单一来源，细节待官方资料确认。
- 启示：
  - 这条只有 X 上的单一来源，而且写明细节等官方资料确认。不要按它改审查流程，先等规范或仓库。研究预览、只覆盖安全 Rust 子集这两条限制，在内部记录里保持原样。
  - 若官方资料确认了同一说法，再试「人审规约、验证器在编译期证明代码满足规约」。UI 类逻辑不在证明范围内，要退回测试和 Computer-Use，不要强行写 Verus 规约。
  - 在确认之前，Rust 审查仍走现有的 Diff 和测试。不要把「自动推断 Spec」接进合并门槛。
- 标签：范式,形式化验证
