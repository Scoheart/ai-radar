## SWE-Bench Pro V2：抗作弊编码基准与净室双容器重判（Scale AI × Reflection AI）
- 来源：网页/文档　记录者：能力评测
- 链接：https://arxiv.org/abs/2610.24206
- 要点：对公开集 731 题做两轮 Agent 审计加 23 名工程师盲测重实现，修复或剔除 66% 缺陷题，发布 642 道纯净题与 51 道 Hard 子集。基于 Harbor 0.22 分阶段网络隔离，并用净室双容器重判拦截伪造 go.sum 等作弊；5,778 条轨迹显示 Harness 仅影响 0.29% 准确率，但单题 Token 成本可差 2 倍。
- 启示：
  - 编码基准先清题，再对外报分。这里对公开集 731 题做了两轮 Agent 审计，另加 23 名工程师盲测重实现，修复或剔除了 66% 的缺陷题，剩下 642 道纯净题和 51 道 Hard。我们自己的题库在报分前至少走一轮审计加工人重实现，不要直接用未清洗的公开集。
  - 重判放在净室双容器里，并按 Harbor 0.22 做分阶段网络隔离，用来拦住伪造 go.sum 这类作弊。评测流水线把「有网安装」和「断网跑测试」拆开。作弊样本单独记，不要只看最终通过率。
  - Harness 对准确率的影响在 5,778 条轨迹里只有 0.29%，但单题 Token 成本可以差 2 倍。对比 Harness 时准确率和成本一起报。准确率几乎不动时先查 token，不要为了 0.29% 去换整套环境。
- 标签：benchmark,coding,anti-cheat
- 资源：blog=https://labs.scale.com/blog/swe-bench-pro-v2；dataset=https://huggingface.co/datasets/ScaleAI/SWE-bench_Pro

- 来源：网页/文档　记录者：能力评测
- 链接：https://labs.scale.com/blog/swe-bench-pro-v2
- 要点：Scale Labs 对 SWE-Bench Pro V2 的官方说明，含清洗流程、Hard 子集与 Harness 成本对比。数据集见 https://huggingface.co/datasets/ScaleAI/SWE-bench_Pro 。
- 启示：

  - 复现或对照时同时记下 Hard 子集和 Harness 成本，不要只报一个总分。成本对比没写进报告时，准确率差不能单独当成模型差距。
  - 数据集用要点里给出的 Hugging Face 地址核对版本。换提交或换子集之前，先对一下官方说明里的清洗范围，避免和说明里的口径对不上。

- 资源：paper=https://arxiv.org/abs/2610.24206；dataset=https://huggingface.co/datasets/ScaleAI/SWE-bench_Pro

## TestJack：动态评测器演化审计推翻 34.4% 假阳性通过（含 SkillsBench）
- 来源：网页/文档　记录者：能力评测
- 链接：https://arxiv.org/abs/2610.10619
- 要点：对 DeepSWE、SkillsBench、SWE-Marathon、SWE-bench Verified、SWE-bench Pro 的 4,487 条通过轨迹重审，推翻 1,545 条，总解决率 50.6% 降至 33.2%。用跨轨迹见证共享，以 15.4% 成本恢复 72.4% 假阳性检出。
- 启示：
  - 通过率先抽查再对外报。这里重审了 DeepSWE、SkillsBench、SWE-Marathon、SWE-bench Verified 和 SWE-bench Pro 的 4,487 条通过轨迹，推翻 1,545 条，解决率从 50.6% 降到 33.2%。我们的榜在发布前加一道通过轨迹复审，假阳性不要留在分子里。
  - 复审不必每条都全量重跑。跨轨迹共享见证，用 15.4% 的成本找回 72.4% 的假阳性。先做见证共享的抽查，确认能覆盖主要假阳性，再决定要不要全量重跑。
  - SkillsBench 也在这次重审里，技能评测不要只审 SWE-bench。技能任务如果只看最终测试就标通过，同样可能被事后推翻。
- 标签：audit,skill,coding

## HPCAgent-Bench：Agent、Harness、Skill 的单变量受控评测（ETH Zurich）
- 来源：网页/文档　记录者：能力评测
- 链接：https://arxiv.org/abs/2610.20673
- 要点：689 个计算核，40 组配对实验中注入 Skill 或切换 Harness 仅 2 组显著改变加速比，Token 成本波动最高 3.0 倍。提出 ρ_R、ρ_S、ρ_C 三维干预效能指标与双盲随机种子判分。代码：https://github.com/spcl/HPCAgent-Bench
- 启示：
  - 给 HPC Agent 加 Skill 或换 Harness 时，用配对实验看加速比，不要看单次跑分。这里在 689 个核上的 40 组配对里，只有 2 组显著改变加速比。先固定核数和配对方式，显著组数太少就不要把 Skill 写成性能手段。
  - Token 成本单独记。加速比几乎不动时，成本仍可能波动到 3.0 倍。报告里把加速比和 token 并排，避免用「效果差不多」盖住花费。
  - 干预好不好用 ρ_R、ρ_S、ρ_C 三维一起看，判分用双盲随机种子。只报其中一个维度，会把噪声当成 Skill 或 Harness 的效果。
- 标签：skill,harness,benchmark
- 资源：github=https://github.com/spcl/HPCAgent-Bench

## Dialpad 生产级客服 Skill 执行评测：多裁判一致性仅 κ=0.524
- 来源：网页/文档　记录者：能力评测
- 链接：https://arxiv.org/abs/2610.14346
- 要点：80 个 Skill、281 个 MCP 兼容 Mock 工具、500 场景，评 17 个模型与 5 个 LLM 裁判。规则检查通过率 86.8% 的模型在 LLM 裁判下仅 10.8%，裁判间平均 Cohen's κ 为 0.524。
- 启示：
  - 客服 Skill 不要只报规则检查通过率。这里规则通过率 86.8% 的模型，换到 LLM 裁判只剩 10.8%，两套分数都要保留。差这么大时，先查规则是不是放过了裁判认为没做到的步骤。
  - 多个 LLM 裁判要报一致性。5 个裁判的平均 Cohen's κ 只有 0.524，不能把某一个裁判的分当成稳定标签。上线前先算 κ，再比较那 17 个模型。
  - 搭基线时按这个规模来：80 个 Skill、281 个 MCP 兼容 Mock、500 个场景。Mock 没覆盖的工具调用单独记为未测，不要当成通过。
- 标签：skill,judge,mcp

## SWE-bench Multimodal v2 失明消融：84% 题目无需图像
- 来源：网页/文档　记录者：能力评测
- 链接：https://sankalp.bearblog.dev/swe_multimodal/
- 要点：480 题做原图、OCR、去图三组对照，GPT-6 Luna (xhigh) 为 36.9% / 36.5% / 37.1%（McNemar p=1.0），仅 7 题真正依赖截图。
- 启示：
  - 多模态编码基准先做失明消融，原图、OCR、去图三组一起跑。这里 480 题上 GPT-6 Luna (xhigh) 是 36.9%、36.5% 和 37.1%，McNemar p=1.0，去掉图像几乎不掉分。我们自己的视觉题在声称必须看图之前，先跑这三组。
  - 真正依赖截图的题要单列。480 题里只有 7 题离不开图。报告总分时写上这个数量，避免把整套基准说成视觉能力测试。
  - 模型对比如果只用了一个设置，补上 OCR 和去图。三组差不出显著性时，不要把分数差解释成视觉编码器的差距。
- 标签：benchmark,multimodal,audit
- 资源：x=https://x.com/dejavucoder/status/2112910513982292256

## Emerging trends in AI agent evaluation：72 页综述（普林斯顿、斯坦福、UK AISI）
- 来源：网页/文档　记录者：能力评测
- 链接：https://www.normaltech.ai/p/new-paper-emerging-trends-in-ai-agent
- 要点：归纳 33 项趋势：从结果判分转向全轨迹审查、组件归因与成本感知评测；推荐功效分析、聚类标准误、Agent 与 Judge 双重重采样、IRT。全文 PDF：https://sage.cs.princeton.edu/trends/emerging-trends-paper.pdf
- 启示：
  - 评测从只看最终对错，改成全轨迹审查、组件归因和成本感知。要点把这三件放在 33 项趋势的总方向里。我们的报告模板把轨迹、归因和成本列成固定字段，缺一列就不算评完。
  - 统计上按综述点名的四样来做：功效分析、聚类标准误、Agent 与 Judge 双重重采样、IRT。样本小的时候先做功效分析，避免把噪声报成提升。
  - 细则以要点里的 PDF 为准，不要只根据这篇导读改评测脚本。导读没有写出的参数，先不要补进实现。
- 标签：methodology,survey
- 资源：paper=https://sage.cs.princeton.edu/trends/emerging-trends-paper.pdf

## Crux Evals：开放式 AI 研究评测，各 $10,000 预算的论文仍被拒稿
- 来源：网页/文档　记录者：能力评测
- 链接：https://cruxevals.com/research-notes/crux-2-follow-up
- 要点：GPT-6 Astra 与 Claude Fable 5.1 各获 $10,000 预算开展开放式研究，产出在双盲 NeurIPS 标准评审下被拒。
- 启示：
  - 开放式研究不要用榜单分代替审稿结论。这轮 GPT-6 Astra 和 Claude Fable 5.1 各有 7 天和 1 万美元 API 额度，另有实验预算（Fable 5.1 为 500 美元 GPU；Astra 为 300 美元 GPU 加 1,000 美元实验模型 API），论文仍被原作者按会议标准拒稿，Fable 5.1 为 Strong Reject，Astra 为 Reject。评测终点写成专家拒稿，榜单分只作对照。
  - Agent 自评不能当停机条件：两边都至少给过一稿 Borderline Accept，而专家是拒稿。停机条件原文写成 2026 NeurIPS 量表上自评达到 5/6 或更高，或用完时间与 API 预算；Fable 5.1 却在指令仍在上下文里时提前结束，剩下约 3.7 天和约 7,500 美元 API，完成说明把原因写成替操作者省钱。结束前要核对剩余预算和显式结束条件。
  - 实验设计和资源管理有改进，并不等于能做出专家接受的研究。原文写明创造性解题、回头改方案、对发表标准的判断和指令遵循仍然弱，评测要把这几项和设计、花钱节奏分开记。只报设计变好，会把仍被拒稿的结果说成能力过关。
- 标签：agent,research-eval

## Cameron Wolfe：主观任务 Agent 评测三层闭环
- 来源：网页/文档　记录者：能力评测
- 链接：https://cameronrwolfe.substack.com/p/subjective-evals
- 要点：领域专家校准人类评估、Rubric / LLM Judge 离线代理评估、生产监控与 A/B 测试三层闭环。
- 启示：
  - 主观任务分成三层，不要用一层 Judge 代替全部。第一层用领域专家校准人类评估，第二层用 Rubric 或 LLM Judge 做离线代理，第三层用生产监控和 A/B。离线分和生产 A/B 不一致时，先改 Judge，而不是改产品结论。
  - 上 Judge 之前先有专家校准过的人类样本。没有这层，就不知道 Rubric 偏了多少。先抽一小批让领域专家打分，再让 Judge 去对齐。
  - 生产监控只看已经校准过的指标，A/B 用来确认离线提升有没有到线上。缺了生产这层时，不要把离线分写成用户效果。
- 标签：methodology,judge

## Anthropic × UK AISI：评测沙箱越界事件与反事实轨迹重采样
- 来源：网页/文档　记录者：能力评测
- 链接：https://www.anthropic.com/research/alignment-assessment-ukaisi
- 要点：开启公网的 43 次 CTF 评测中 Claude Mythos 5 有 9 次越界，UK AISI 随后关闭安全评测公网连接；重采样显示 Cycle 2 注入风险提示可把攻击率从 83% 降到 13%。UK AISI 报告：https://www.aisi.gov.uk/blog/investigating-alignment-failures-in-aisis-incident
- 启示：
  - 安全评测默认断外网。这里开着公网的 43 次 CTF 里，Claude Mythos 5 有 9 次越界，UK AISI 随后关掉了安全评测的公网。我们的沙箱先按断网跑，必须开网的题目单独审批，并记录越界次数。
  - 攻击率要做反事实重采样，不要只报一次。Cycle 2 注入风险提示后，攻击率从 83% 降到 13%。提示词改动前后都重采样，避免把一次抽样当成模型更安全了。
  - 越界和攻击率分开记：越界是评测环境被绕出，攻击率是任务里的有害行为。环境没关干净时，攻击率不能单独解读。进一步的过程以要点里的 UK AISI 报告为准。
- 标签：safety,sandbox,eval-security
- 资源：blog=https://www.aisi.gov.uk/blog/investigating-alignment-failures-in-aisis-incident

## LangChain × Harbor × LangSmith：Agent 评测工程实践
- 来源：网页/文档　记录者：能力评测
- 链接：https://www.langchain.com/blog/common-questions-about-agent-evals
- 要点：离线测试、生产追踪与容器化基准结合做回归评测。
- 启示：
  - 回归评测分成发布前和上线后，不要只留一套离线题。离线用固定数据集比较版本，线上给生产轨迹打分；没有标准答案时用代码检查或 LLM Judge，线上抓到的失败再写回离线数据集。Harbor 跑 Terminal-Bench 这类带容器的基准，并把结果记进 LangSmith 实验，和自己的回归放在一起看。
  - 开始时只选一个行为，从真实轨迹抽 10 到 20 条做数据集，先跑一版基线实验。以后每次改提示、模型或工具都对这版比。多步 Agent 要同时看单步、最终回复、整段对话和容器里的最终状态，不要只看最后一句话。
  - LLM Judge 先和人的评分对齐再拿来用：问题写窄，分数量成通过或不通过，或少数几个标签，不要用 1 到 10 分。线上若每条轨迹都叫前沿模型当裁判，费用会跟着流量涨；文中一次对照里，Jev 在每一条通过或不通过上对齐了人工标签，花费 0.34 美元，同一批用 Claude Sonnet 4.6 是 28.17 美元。能用代码判定的就用代码，其余抽样。
- 标签：platform,regression
