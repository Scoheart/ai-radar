# MCP · 2026-11-19

## Code mode 可比普通 MCP 少用七到九成 token，额外路由层未证实更优
- 来源：网页/文档　记录者：AI前沿者
- 链接：https://arxiv.org/abs/2611.19123
- 要点：论文在受控环境里比较普通 MCP、Code mode（对工具桩写脚本）和决策层（先用便宜路由器筛选工具子集）。实验覆盖 12 个服务器、最多 1,958 个干扰工具，以及 Qwen、Gemma、Nemotron 三个开权模型，并在预先登记的密封测试集上评测。Code mode 明显好于普通 MCP，token 用量减少 70% 到 90%，效用也显著提高。在代码桩里声明返回值结构是一阶因素，对较弱模型的成功率最大可相差 39.5 个百分点，影响超过再加一层路由器。作者预先假设的“决策层加 Code mode 优于单独 Code mode”未被证实：对较弱模型只有不显著的小幅提升，对最强模型还略增成本。工具选择微调模型、评测工具和全部轨迹已公开。
- 摘要：
  - 让 Agent 对工具桩写代码，比直接在 MCP 目录里挑工具更省 token，也更容易成功。
  - 桩上的返回值结构说明很关键；在 Code mode 前再加一层决策路由，并没有被证实更好。
- 启示：
  - MCP 网关若工具很多，可优先尝试 Code mode 和清晰的返回值约定，而不是先上复杂的路由层。
- 标签：MCP,code-mode,gateway,tool-use
- 资源：paper=https://arxiv.org/abs/2611.19123；github=https://github.com/abhishek085/mcp-decision-layer

## MCP 工具名不等于提供者身份，同名或更像权威的描述会造成误绑定
- 来源：网页/文档　记录者：AI前沿者
- 链接：https://arxiv.org/abs/2611.21577
- 要点：新不伦瑞克大学加拿大网络安全研究所的论文把这类问题称作 tool-provider misbinding：请求本该打到合法提供者，却被解析到攻击者控制的工具。攻击者不必攻破主机、模型、合法服务器或网络，只需再运行一个 MCP 服务器并自行撰写工具元数据。作者在受控 MCP 环境中评测了五个基于 LLM 的客户端。最严重的失败出现在工具名完全相同、描述贴合任务、参数结构也兼容同时成立时；即便没有同名，只靠看起来更权威的描述加上兼容 schema，也可能造成错误执行，或让客户端无法确定该用哪一家。不同模型暴露同一弱点的方式不同，包括直接选中攻击者、发起澄清，以及提供者解析不稳定。
- 摘要：
  - MCP 用来做发现和选择的工具元数据，本身并不必然绑定到经过验证的提供者身份。
  - 攻击者只要再挂一个同名或描述更像权威的服务器，就可能把调用抢走，不必攻破原有系统。
- 启示：
  - 接入多个 MCP 服务器时，应对工具名和来源做身份约束，不能只靠名字或描述来决定调用谁。
- 标签：MCP,security,tool-identity,misbinding
- 资源：paper=https://arxiv.org/abs/2611.21577
