## SEP-2640 Skills over MCP 成为官方扩展
- 来源：网页/文档　记录者：MCP与Skills
- 链接：https://modelcontextprotocol.io/seps/2640-skills-extension
- 要点：通过 MCP Resources 分发 SKILL.md（skill:// URI），新增 skills/list、skills/get；要求内容哈希绑定审批、按服务端身份隔离命名空间、忽略远端 allowed-tools，并移除归档分发。
- 启示：
  - Skills 若经 MCP 分发，走 Resources 和 skill:// URI，并实现 skills/list 与 skills/get。不要再发归档包。客户端只接受这两种读取方式。
  - 审批绑在内容哈希上。哈希变了就重新审批，不能沿用旧批准。命名空间按服务端身份隔开，避免两个服务器的同名 Skill 撞在一起。
  - 忽略远端带过来的 allowed-tools。工具允许列表以本地策略为准。远端清单只能当说明，不能当成已经授权。
- 标签：mcp,skills,sep
- 资源：spec=https://plan.modelcontextprotocol.io/seps

## MCP 2026-07-28 无状态核心规范
- 来源：网页/文档　记录者：MCP与Skills
- 链接：https://blog.modelcontextprotocol.io/posts/2026-07-28/
- 要点：移除 initialize 握手、Mcp-Session-Id 与 GET SSE，单 POST 携带 _meta，用 Mcp-Method/Mcp-Name 头路由，以 MRTR input_required 替代服务端反向长连接。
- 启示：
  - 客户端适配 2026-07-28 时，去掉 initialize 握手、Mcp-Session-Id 和 GET SSE。每个调用改成一次 POST，元数据放在 _meta，路由看 Mcp-Method 和 Mcp-Name 头。先改网关的路由，再改客户端，避免一半还在等会话。
  - 需要中途补充输入时，用 MRTR 的 input_required，不要再维持服务端反向长连接。input_required 在状态机里是未完成，不要记成工具成功。
  - 旧会话在无状态端点上接不住。迁移期用单独的旧入口，不要在同一个 POST 上兼容两种会话模型。缺 _meta 或缺少方法头的请求明确拒绝。
- 标签：mcp,spec
- 资源：github=https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/blog/content/posts/2026-07-28-spec-ga/index.md

## SEP-3415 Events 扩展：轮询、流式、Webhook 三种事件投递
- 来源：网页/文档　记录者：MCP与Skills
- 链接：https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415
- 要点：定义 events/list 与 poll、stream、subscribe（Standard Webhooks 签名）三种投递，支持游标续传，服务无人值守场景。
- 启示：
  - 无人值守的任务不要只靠一条挂着的连接。按 SEP-3415 提供 events/list，以及 poll、stream、subscribe 三种投递。subscribe 用 Standard Webhooks 的签名校验，验签失败就丢掉，不要先处理再验。
  - 续传用游标，客户端记下最后收到的位置。消费者重启之后从游标继续，而不是从头重放已经执行过副作用的事件。
  - 有副作用的处理做成幂等。poll 和 stream 可能看到同一事件。在这条 SEP 落地之前，不要把这三种写成已经承诺的公网接口，先在内部任务上试 poll 加游标。
- 标签：mcp,sep,events

## SEP-2848 工具调用异步审批
- 来源：网页/文档　记录者：MCP与Skills
- 链接：https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2848
- 要点：可申请批准的拒绝返回 Task 句柄，带外审批后重验权限并以 at-most-once 执行，客户端用 tasks/get 轮询。
- 启示：
  - 工具调用被拒绝但可以申请批准时，返回 Task 句柄，不要在拒绝响应里直接执行。人在带外批准之后，必须重新验一次权限，再按 at-most-once 执行。执行器用句柄做幂等键，重复批准不能跑第二次。
  - 客户端用 tasks/get 轮询结果，不要假设拒绝响应里已经带了执行输出。轮询间隔和超时写进调用方，避免批准后无人取结果。
  - 批准人和原调用的权限分开记。重验失败就保持未执行，并把原因写回 Task。不要因为已经点了批准就跳过第二次鉴权。
- 标签：mcp,sep,auth
- 资源：spec=https://plan.modelcontextprotocol.io/seps

## SEP-2643 结构化授权拒绝
- 来源：网页/文档　记录者：MCP与Skills
- 链接：https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2643
- 要点：传输无关的拒绝信封，提供 URL elicitation、Tasks 异步审批、OAuth scopes/RFC 9396 RAR 三类修复提示。
- 启示：
  - 授权失败用统一的拒绝信封，不要每个传输各写一种错误字符串。信封里的修复提示分成三类：URL elicitation、Tasks 异步审批、OAuth scopes 或 RFC 9396 的 RAR。客户端按类型分支，不解析散文。
  - 没有对应能力的客户端，把未知提示显示成需要额外授权，不要当成工具执行失败而自动重试。自动重试会把拒绝打成请求风暴。
  - 三类提示可以同时缺。缺提示时不要猜该去申请哪个 scope。先把信封解析和日志做了，再接具体的审批流。
- 标签：mcp,sep,auth
- 资源：spec=https://plan.modelcontextprotocol.io/seps

- 要点：AutoCrawler 从 IDL 生成工具 Schema，Sidecar 协议转换与 PII 脱敏；Omni MCP 渐进发现、Response Projection 字段裁剪、Code Mode 落盘后 grep。
- 启示：
  - 工具数量到 800 多个 Server、5000 多个工具时，不要把全部 Schema 塞进上下文。用渐进发现：先给目录，再取单个工具的 Schema。我们的网关在工具数上去之前就按这个顺序做，而不是等上下文爆了再改。

## MCP 授权：弃用 DCR 转向 CIMD
- 来源：网页/文档　记录者：MCP与Skills
- 链接：https://www.scalekit.com/blog/mcp-authorization-guide
- 要点：CIMD 以 HTTPS URL 作 client_id，客户端校验 iss；网关做双面 OAuth，PKCE S256 加 RFC 8707 resource 绑定，禁止 Token 透传。
- 启示：
  - 新客户端注册走 CIMD，不再依赖动态客户端注册。client_id 用 HTTPS URL，并校验 iss。授权服务器拒绝没有 URL 形态 client_id 的新客户端，旧的 DCR 客户端单独列清单。
  - 网关做双面 OAuth：面向下游验证调用方，向上游另换凭据。PKCE 用 S256，并用 RFC 8707 把 token 绑到 resource。缺 resource 绑定的 token 不要接受。
  - 禁止把上游 token 透传给下游。审计日志里区分网关自己发出的 token 和上游 token。透传路径在代码审查里当成缺陷，而不是一个配置开关。
- 标签：auth,gateway

## Zuplo MCP Gateway 双面 OAuth 与无状态路由
- 来源：网页/文档　记录者：MCP与Skills
- 链接：https://zuplo.com/docs/mcp-gateway/how-it-works
- 要点：网关对下游是 OAuth 2.1 资源服务器、对上游独立换取凭据，基于请求头实现无状态水平扩展。
- 启示：
  - 网关对下游扮演 OAuth 2.1 资源服务器，对上游单独换凭据，两边的 token 不要混用。配置把「验证下游 token」和「向上游取 token」分成两个步骤，这样加实例时可以不带会话。
  - 路由状态放在请求头里，不放在网关内存里的会话。加实例时不需要会话粘滞。头缺失就拒绝，不要退回到本机缓存的上一跳。
  - 换凭据失败和下游鉴权失败用不同的错误。上游超时不应被客户端理解成自己的 token 无效而反复登录。
- 标签：gateway,auth

## Microsoft MCP Gateway 适配 2026-07-28
- 来源：网页/文档　记录者：MCP与Skills
- 链接：https://github.com/microsoft/mcp-gateway/blob/main/docs/mcp-2026-07-28.md
- 要点：Microsoft 网关对无状态新规范的适配说明。
- 启示：
  - 升到这份无状态网关前，先确认 MCP 客户端和每个 adapter 都支持 2026-07-28。文档写明这一版不会做协议降级，也没有 legacy 开关；做不到的继续钉在兼容的旧镜像上。新旧镜像不要放进同一个后端池，切换流量前先排空，旧的传输会话不能在新版本上续上。
  - 每个请求独立鉴权再转发，不再用 Mcp-Session-Id、Last-Event-ID 或 session_id 查询参数选后端。需要跨调用记住状态时，让工具返回显式句柄，下次当参数传回去。公共路径仍是 /mcp，adapter 走 /adapters/{name}/mcp；/sessions 下的会话和 MCP 传输会话不是一回事，不要一起删。
  - 请求要带 MCP-Protocol-Version: 2026-07-28、Mcp-Method，以及 tools/call、prompts/get、resources/read 所需的 Mcp-Name；params._meta 里要有协议版本和 clientCapabilities，Accept 同时包含 application/json 和 text/event-stream。input_required 是未完成，不是工具成功；响应流被关掉会取消请求，有副作用的工具不要因为连接失败就自动重试。单次请求体不要超过 4 MB。
- 标签：gateway

## DVARA 网关治理 MCP Apps：页面指纹锁定
- 来源：网页/文档　记录者：MCP与Skills
- 链接：https://dvarahq.com/docs/mcp-gateway/apps
- 要点：固定 ui:// 页面哈希并校验 _meta.ui.csp 与 permissions，页面变更触发隔离重审。
- 启示：
  - 网关对 MCP App 锁定 ui:// 页面的哈希。哈希变了就隔离并重新审查，不要沿用上一次的放行。发布时把哈希写进审批记录。
  - 同时校验 _meta.ui.csp 和 permissions。只对哈希、不看 CSP 和权限，页面仍可能再要剪贴板或更宽的源。任何一项变了都要重新隔离。
  - 重审完成前，这个页面不要回到共享宿主。隔离指的是不和已批准的 App 共用同一执行环境。
- 标签：mcp-apps,gateway,security
