## NVIDIA 开源 SkillSpector 技能安全扫描器
- 来源：网页/文档　记录者：MCP与Skills
- 链接：https://github.com/NVIDIA/SkillSpector
- 要点：静态分析加可选 LLM 语义评估，17 类 71 种模式，输出 0–100 风险分与 SARIF；引用数据称 31,132 个开源技能中 26.1% 有漏洞。
- 启示：
  - 技能入库前跑静态扫描。模式按 17 类 71 种覆盖，输出 SARIF，以便进现有的代码扫描流水线。0 到 100 的风险分要配上命中的模式，不要只留一个分数。
  - LLM 语义评估是可选的。默认可先只开静态，语义评估单独记成本和误报。不要把两类结果合成一个分，还不标注来源。
  - 26.1% 来自他们引用的 31,132 个开源技能。内部库先用这套扫描跑一遍再引用比例，不要把这个数字写成我们仓库的漏洞率。
- 标签：skills,security

## agent-skills-eval：SKILL.md 双轨基线评测运行器
- 来源：网页/文档　记录者：MCP与Skills
- 链接：https://github.com/darkrishabh/agent-skills-eval
- 要点：with_skill 对 without_skill 基线，量化提升、延迟与 Token；含邻近负例与确定性轨迹断言。
- 启示：
  - 每个 Skill 都跑 with_skill 和 without_skill 两轨，提升、延迟和 token 一起报。没有无技能基线的分数不要进看板。两轨放在同一批任务上。
  - 加邻近负例：和技能很像、但不该触发的请求。只测该触发的正例，会把描述写得过宽的技能放进去。
  - 轨迹用确定性断言，例如必须调用的工具或必须留下的文件。断言失败要能指出轨迹里的哪一步。若要加模型评分，放在确定性断言之后，并且不要替代这两轨对比。
- 标签：skills,eval

## OpenAI：用 evals 系统化测试 Agent Skills
- 来源：网页/文档　记录者：MCP与Skills
- 链接：https://developers.openai.com/blog/eval-skills
- 要点：显式、隐式、带噪触发与负例测试集，优先确定性检查，再用结构化 LLM Judge。
- 启示：
  - 测试集按四类来：显式点名技能、描述匹配但不点名的隐式触发、带领域噪声仍应触发的请求，以及不该触发的负例。文中单个技能从 10 到 20 条 prompt 起步。每个技能至少有一条负例，防止描述过宽。
  - 先做确定性检查。用 codex exec --json 的轨迹看有没有执行规定命令、有没有生成规定文件，失败时能指出是哪一条事件。结构化 Judge 用 --output-schema 收成固定 JSON，只评风格和约定，不代替确定性检查。
  - 成功标准在写技能之前就分成结果、过程、风格和消耗。name 和 description 是触发依据，含糊就先改 frontmatter，再改正文。手动跑一次发现的偏差写成下一行用例，而不是只改技能不留测试。
- 标签：skills,eval

## LangChain：Evaluating Skills
- 来源：网页/文档　记录者：MCP与Skills
- 链接：https://www.langchain.com/blog/evaluating-skills
- 要点：技能评测工程实践，涵盖多技能共存下的触发与误调问题。
- 启示：
  - 评 Skill 时固定一套任务，先跑无 Skill 基线，再跑有 Skill，两边环境要干净且一致。文中用 Docker 跑 Claude Code，也提到可以用 Harbor 或其他沙箱。不隔离的话，Agent 会先翻目录，起点不同，分差不能算在 Skill 上。
  - 同时记四件事：该调用时有没有调用、不该调用时有没有误调用、任务完成了多少步、用了多少轮和多少墙钟时间。约 20 个相近的 LangGraph Skill 时会叫错，收到 12 个就能稳定叫对；触发不稳定时，把何时用哪个 Skill 写进总会加载的 AGENTS.md 或 CLAUDE.md，文中一条创建 Agent 的任务即使提示去调用，命中率也只到 70%。
  - 不要只看总完成率。文中带 Skill 的完成率是 82%，不带是 9%，但不同的拆分在不同任务上好坏不一样。用轨迹看它读了什么、有没有真正用到 Skill，再改 Skill 里的一块重新跑，避免把整份一次改完后对不上原因。
- 标签：skills,eval

## Phil Schmid：评测与测试 Agent Skills 实战指南
- 来源：网页/文档　记录者：MCP与Skills
- 链接：https://www.philschmid.de/testing-skills
- 要点：技能测试的实操流程与指标。
- 启示：
  - 写 Skill 之前先定可检查的成功标准，按结果、是否遵守指令，以及时间和 token 打分，不要只看路径对不对。文中的 Gemini Interactions API Skill 用同一套检查从 66.7% 做到 100%。每个 Skill 先写 10 到 20 条自带成功条件的 prompt，再谈扩规模。
  - 触发写在 frontmatter 的 name 和 description 里：描述含糊会该触发时不触发，写得太宽又会误触发，文中改描述这一项就修掉了 7 个失败里的 5 个。负例要单列，确认不该用这个 Skill 的请求不会命中。指令用祈使句写死做法，不要只写「推荐」。
  - 能用正则或文件是否存在判定的，先做确定性检查，LLM Judge 只留给结构、命名这类说不清的项；这篇 Interactions API 评测就没有用 Judge。每条用例隔离环境，同一题跑 3 到 5 次看分布。若卸掉 Skill 之后用例仍然通过，说明模型已经学会，这个 Skill 可以退役。
- 标签：skills,eval
