## CorpusMap：以实体为中心的 Agentic Search 导航层
- 来源：网页/文档　记录者：知识库
- 链接：https://arxiv.org/abs/2609.37226
- 要点：离线四阶段构建实体-文档二分图并渲染带来源路径的实体页，与原文并存；三大基准回答质量提升 6.4–11.7 分，输入 Token 减少 34%–57%。适用跨源多跳企业检索。
- 启示：
  - 跨源多跳检索先加一层实体导航，不要只加长上下文。CorpusMap 离线分四阶段建实体-文档二分图，渲染带来源路径的实体页，和原文放在一起。先选一个多跳问题集，看 Agent 是不是沿着来源路径走。
  - 验收同时看质量和 token。三大基准上回答质量提高 6.4 到 11.7 分，输入 token 减少 34% 到 57%。只涨质量而 token 不降，或只省 token 而质量掉出这个区间，都不要算做成。
  - 实体页必须带来源路径，并和原文并存。页上写了结论但点不回来源时，这层导航不要上线。适用的是跨源多跳的企业检索，单文档问答不必先上。
- 标签：agentic-search,graph

## Librarian Agents：用 RL 预构建可导航的文件系统工作区
- 来源：网页/文档　记录者：知识库
- 链接：https://arxiv.org/abs/2610.22273
- 要点：Builder Agent 经 GRPO 训练，用创建/合并/删除操作把语料重组为带溯源链接的层级文件系统；BrowseComp-Plus 准确率 75%–77%，约 10 次查询摊平构建成本。
- 启示：
  - 查询时现搜之前，先试预构建工作区。Builder Agent 用 GRPO 训练，只通过创建、合并、删除把语料收成带溯源链接的层级文件系统。先拿一块语料跑这三种操作，确认每条文件都能点回原文。
  - 用 BrowseComp-Plus 看准确率，这里是 75% 到 77%。构建成本按大约 10 次查询来摊平。查询量到不了这个次数的库，先不要付预构建的账。
  - 溯源链接是准入条件。重组后的文件如果丢了来源，准确率即便落在 75% 到 77%，也不要替换现有检索。
- 标签：agentic-search,rl
- 资源：github=https://github.com/teresaz05/librarian-agents；project=https://librarian-agents.github.io/；x=https://x.com/chelseabfinn/status/2113036636586131475

## Karpathy LLM Wiki 范式
- 来源：网页/文档　记录者：知识库
- 链接：https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f
- 要点：Raw Sources + LLM 维护的 Markdown Wiki + Schema 三层结构，配 index.md/log.md 与 Ingest/Query/Lint 闭环，让知识持续累积；规模大时可挂本地混合检索 qmd。
- 启示：
  - 知识库按三层放：原始来源、LLM 维护的 Markdown Wiki、Schema。配上 index.md 和 log.md，把写入收成 Ingest、Query、Lint 闭环。先让 Lint 能抓到 Wiki 和来源对不上的条目，再增加自动写入。
  - 查询打到 Wiki，不要每次都把原始材料塞进上下文。原始来源留着给 Lint 和人工核对。Schema 约束页面的结构，避免模型每次发明一种格式。
  - 规模变大再挂本地混合检索 qmd，不要一开始就上独立向量库。qmd 挂上之后，Lint 仍以 Markdown 为准，检索结果要能回到对应页面。
- 标签：wiki,personal-kb

## Tencent/WeKnora：混合检索 RAG + Agent + 自维护 Wiki
- 来源：网页/文档　记录者：知识库
- 链接：https://github.com/Tencent/WeKnora
- 要点：关键词+向量混合检索、父子分块、Neo4j GraphRAG、ReAct Agent 与自维护 Wiki，内置 MCP Server，可同步飞书/Confluence/Notion。
- 启示：
  - 若要同时具备混合检索、父子分块、图和自维护 Wiki，对照 WeKnora 的组合，而不是各接一块再自己粘。它用关键词加向量、父子分块、Neo4j GraphRAG 和 ReAct Agent，并内置 MCP Server，可以同步飞书、Confluence 和 Notion。先接一个已有文档源，看混合检索和父子分块是不是同时生效。
  - 图用的是 Neo4j。已经有图数据库时，先确认能替换或并存，不要为了这个平台再复制一份图。ReAct Agent 和 Wiki 的写入权限分开，避免 Agent 把检索结果写回成新的事实。
  - MCP Server 对外暴露前，列清同步进来的源有没有权限边界。飞书和 Confluence 的文档不要因为接了 MCP，就变成所有 Agent 默认可读。
- 标签：platform,wiki
- 资源：docs=https://weknora.weixin.qq.com

## NVIDIA Nemotron 3.5 检索三件套（Parse/Embed/Rerank）
- 来源：网页/文档　记录者：知识库
- 链接：https://huggingface.co/blog/nvidia/nemotron-retriever-world-class-agentic-retrieval
- 要点：631M 解析模型单张 H100 约 10.5–16.1 页/秒；多模态 Embed 与 Rerank 让 Agentic Search 单次查询 Token 降低 13%–14%。
- 启示：
  - 文档解析选型时，把这个 631M 的 Parse 模型和现有解析器比吞吐。原文是单张 H100 大约 10.5 到 16.1 页/秒。先用我们自己的版式样本测页/秒，不要只看参数量。
  - Agentic Search 的 token 要单独量。多模态 Embed 加 Rerank 在原文里让单次查询 token 降了 13% 到 14%。打开和关闭这两件套各跑一批查询，降幅出不来就不要为了多模态加调用。
  - Parse、Embed、Rerank 分开替换。三件套绑在同一次查询里时，分不清是解析变好还是重排变好。先换解析，再加 Embed 和 Rerank。
- 标签：parsing,embedding,rerank
- 资源：hf=https://huggingface.co/nvidia/Nemotron-3.5-Parse；docs=https://docs.nvidia.com/nim/ingestion/parse/latest/getting-started.html

## Qdrant 1.20：原生全文 BM25、code 分词器与 turbo 量化

- 链接：https://qdrant.tech/blog/qdrant-1.20.x/
- 要点：无需额外稀疏向量管道即可单请求做 Dense+BM25 混合检索；新增代码标识符分词、nested 逐元素索引与 turbo16/turbo8 量化。
- 启示：

  - nested 逐元素索引和 turbo16、turbo8 量化分开开。量化会改存储和精度，先在一份副本上量召回下降，再替换生产集合。不要四样同一天全开，出了问题对不上是哪一项。

## SAG：查询时动态超边的本地优先检索
- 来源：网页/文档　记录者：知识库
- 链接：https://github.com/Zleap-AI/SAG
- 要点：入库转为 Event+Entity 锚点，不预建全局图谱，查询时用 SQL 关联生成动态超边做多跳；SQLite+LanceDB，内置 MCP Server。
- 启示：
  - 本地优先的检索不要先建全局图谱。SAG 入库只留 Event 和 Entity 锚点，查询时用 SQL 关联拼出动态超边做多跳。先用 SQLite 加 LanceDB 跑通一条多跳问题，确认超边是查出来的，而不是预计算的。
  - 数据和索引放在 SQLite 与 LanceDB，方便单机带走。换到别的数据库之前，先确认动态超边的 SQL 还能复现同一条多跳路径。
  - 内置 MCP Server 暴露前，限定它只能读这些锚点和查询结果。不预建全图的好处是少一份陈旧图谱，权限也要卡在查询接口上，而不是卡在一张静态图上。
- 标签：graphrag,local-first
- 资源：paper=https://arxiv.org/abs/2606.15971；github-benchmark=https://github.com/Zleap-AI/SAG-Benchmark

## Chelsea Finn 解读 Librarian Agents
- 来源：据 X 上的报道　记录者：知识库
- 链接：https://x.com/chelseabfinn/status/2113036636586131475
- 要点：@chelseabfinn 指出纯查询时 Agentic Search 易漏检且重复耗算力，预编译带溯源的文件系统工作区可带来 30%+ 准确率提升。
- 启示：
  - 纯查询时搜索如果又漏又重复耗算力，先试预编译的文件系统工作区，而不是每次现搜。这条解读给出的幅度是 30% 以上的准确率提升，并且工作区要带溯源。先在一个会漏检的查询集上量有没有这个幅度。
  - 30%+ 是这条帖子的说法。复现时用它指向的论文和代码，不要把帖子数字当成我们库上的承诺。提升出不来时，先查溯源链接在不在，再查预编译本身。
  - 预编译会花构建成本。查询会反复发生的语料才值得做。一次性问题继续走查询时搜索，避免为了帖子里的幅度去预编译所有库。
- 标签：agentic-search
